Design review & modernization plan

Rearchitecting Tech Challenge

A 2022 two-VPC EKS stack, read end to end — what it actually does, where it is broken or exposed, and the single-VPC design that replaces it.

Repo github.com/tbadmus/tech-challenge Code as of Jun 2022 · 2f11cf3 Reviewed 10 Sep 2026 Scope 51 files · Terraform, Packer, Jenkins, K8s manifests

The design is sound in intent and obsolete in execution. Keeping worker nodes off the public internet is still right. Everything built to achieve it — a second VPC, a Transit Gateway, an imperative routing script, a public SSH bastion — has been replaced by native capability that did not exist or was not mature in 2022.

Two findings change the risk picture immediately. The cluster you believe is private has a public API endpoint open to 0.0.0.0/0, because endpoint access was never configured and that is the AWS default. And every security gate in the pipeline is decorative — Sonar cannot fail the build, Trivy has no exit code, and its flag was removed from the tool years ago.

What the stack does today

One Terraform root composes eleven hand-rolled modules into two VPCs. network1 (10.0.0.0/16) is public and holds a bastion, an IGW and a NAT gateway. network2 (172.31.0.0/16) has no IGW and no NAT at all, and holds the EKS cluster and its managed node group. A Transit Gateway joins them, and network2's default route points at it — so a pod reaching the internet leaves its VPC, crosses the TGW, and hairpins out through the other VPC's NAT gateway.

That extra hop is the whole reason the repo is shaped the way it is. It is also the reason for routes.sh, a shell script invoked from a null_resource that adds the TGW default-route-table entry with the AWS CLI, because it was never modelled as a Terraform resource. The node group cannot register without that route, which is why module.eks2 carries an explicit depends_on chain.

The app is an Express hello-world behind a Service of type: LoadBalancer annotated internal, so verification means SSH-ing to the bastion and curling from inside. A self-managed Elasticsearch/Fluentd/Kibana stack is applied from raw manifests. A Jenkins declarative pipeline runs Sonar, Trivy, Packer, Terraform, then the two kubectl apply stages.

Question one — are two VPCs still needed?

No. A single VPC with public and private subnets gives you identical isolation, one fewer network hop, and no imperative routing script.

The isolation you want comes from subnet routing, not from a VPC boundary. Nodes in a private subnet have no public IP and no inbound path from the internet whether that subnet sits in its own VPC or beside the public subnets. Splitting them bought no additional containment — it only moved the NAT gateway one hop further away.

There is also a running cost. A Transit Gateway attachment bills roughly $0.05 per hour, so two attachments are about $70–75 a month before data-processing charges — for a demo cluster, spent on a hop that adds nothing. (Verify against current pricing for us-east-1.)

What to keep. The hub-and-spoke pattern is genuinely worth teaching — it is how multi-account and on-premises connectivity actually works. Keep it as an optional module with its own README, off the critical path, so a junior engineer can stand it up deliberately rather than inheriting it as an unexplained dependency.

Question two — can a controller handle the load balancers?

Yes. The AWS Load Balancer Controller creates a real ALB from an Ingress and targets pods directly by IP — so the app is publicly reachable while every node stays private.

Today the Service carries service.beta.kubernetes.io/aws-load-balancer-internal: "true". That is the legacy in-tree annotation, handled by the AWS cloud provider, and what it produces is a Classic Load Balancer — a load balancer type AWS has been steering people off for years. Because it is internal, nothing outside the VPCs can reach it, which is why the README's last step is to SSH into a bastion and run curl.

The controller changes the shape of the answer, not just the implementation. With target-type: ip the ALB registers pod IPs as targets directly, so it can live in the public subnets while its targets live in the private ones. The subnet boundary is crossed by the load balancer, not by the node.

Three details make this a small change rather than a rewrite. The controller discovers subnets by the tags kubernetes.io/role/elb and kubernetes.io/role/internal-elb — modules/vpc already applies both, so that work carries over. It needs an IAM role, which is what EKS Pod Identity is for. And when you do want L4, the same controller produces a modern NLB via aws-load-balancer-type: external instead of a Classic LB.

The payoff beyond reachability is that TLS, WAF association, health checks, path routing and OIDC authentication all become Ingress annotations rather than console clicks — which is exactly the no-ClickOps property the project is meant to demonstrate.

Question three — can the cluster stay private and still be managed?

Yes, and the more urgent point is that it is not private now. Endpoint access was never configured, so the API server is published to the whole internet by default.

modules/eks/main.tf sets only subnet_ids inside vpc_config. The AWS defaults then apply: endpoint_public_access = true, public_access_cidrs = ["0.0.0.0/0"], endpoint_private_access = false. IAM still gates authentication, so this is not an open cluster — but the network posture is the opposite of the one the architecture was built to achieve, and the README's stated reason for the bastion ("cannot be accessed from local without VPN") is not accurate for the API endpoint. It is only true of the internal load balancer.

Network reachability and authorization are separate problems, and the repo currently under-configures both. Three network postures are worth knowing:

Option B in practice is one command, with no inbound security-group rule anywhere:

aws ssm start-session --target $INSTANCE_ID \ --document-name AWS-StartPortForwardingSessionToRemoteHost \ --parameters '{"host":["$EKS_ENDPOINT"],"portNumber":["443"],"localPortNumber":["8443"]}'

The AMI already installs amazon-ssm-agent and the bastion role already carries AmazonSSMManagedInstanceCore, so this path is most of the way built — it just sits unused next to an SSH key pair that does the same job less safely.

Authorization is the other half, and it is the bigger no-ClickOps gap. The repo never sets access_config, so the cluster falls back to the aws-auth ConfigMap and the IAM principal that ran terraform apply is the only administrator. Adding a colleague means hand-editing a ConfigMap in a live cluster — the exact manual step the project exists to eliminate. Setting authentication_mode = "API" and declaring aws_eks_access_entry resources maps SSO permission-set roles to cluster access in Terraform, in code, reviewable in a pull request.

One dependency to plan for: if you go all the way to option C, a private cluster with no NAT needs interface endpoints for ecr.api, ecr.dkr, logs, sts, ec2 and elasticloadbalancing, plus the S3 gateway endpoint — otherwise image pulls and log shipping fail with no obvious cause. That is a good teaching moment in itself.

Findings

Every item below was confirmed by reading the code, not inferred. Line references are against commit 2f11cf3.

CriticalThe private cluster has a public API endpointmodules/eks/main.tf:6–8

vpc_config sets only subnet_ids. AWS then defaults to endpoint_public_access = true with public_access_cidrs = ["0.0.0.0/0"] and private access disabled — so the API server is internet-published and the private path was never enabled.

FixSet endpoint_private_access = true, restrict public_access_cidrs, and add the CIDR list as a variable so environments differ without editing modules.

CriticalAll 65,535 TCP ports open to the peer VPCmodules/eks/main.tf:46–54

aws_security_group_rule.ec2 allows from_port 0 to to_port 65535 from var.external_cidr, which is the entire 10.0.0.0/16 VPC. It attaches to the EKS cluster security group, which is also applied to managed node group instances — so anything in the other VPC has full TCP reach to the control plane and every node.

FixNarrow to :443 from named sources. In the single-VPC design this rule disappears with the second VPC.

CriticalA private key is generated into the repo root, and .gitignore does not cover itbootstrap.sh:4 · .gitignore · main.tf:135–141

bootstrap.sh writes an unencrypted RSA key called techkey into the working directory. .gitignore contains three Claude Code entries and nothing else — no techkey, no *.pem, no *.tfstate, no .terraform/. The matching bastion accepts SSH from 0.0.0.0/0, and the imported key pair mvp is shared account-wide.

FixExtend .gitignore first — it is a one-line change guarding a credential leak. Then drop SSH entirely in favour of SSM (option B above); the AMI and the instance role already support it.

CriticalEvery security gate in the pipeline is decorativeJenkinsfile:15–38

Three independent failures. waitForQualityGate abortPipeline: false means Sonar can never fail a build. Neither Trivy invocation passes --exit-code 1, so findings are printed and ignored. And -security-checks was renamed to --scanners years ago while config became misconfig — on any current Trivy the step errors or silently scans nothing.

Fixtrivy fs --scanners vuln,misconfig,secret --exit-code 1 --severity HIGH,CRITICAL app/, and let the quality gate abort. A gate that cannot fail is worse than no gate — it produces a green tick that means nothing.

CriticalA credential is written into tracked YAML during the buildJenkinsfile:76–86

The Elasticsearch password is sed -i'd from a Jenkins credential into all three logging/*.yaml files. It then exists in plaintext in the workspace, in the applied pod spec, and in anything that archives the workspace — and the credential masking Jenkins applies to logs does not extend to files on disk.

FixA Kubernetes Secret sourced from AWS Secrets Manager via the Secrets Store CSI driver or External Secrets Operator. Never templated into a tracked file.

Criticaldev and master deploy to the same state file, with no lockingprovider.tf:18–23 · Jenkinsfile:56–74

The backend hardcodes key = "lb-terraform.tfstate" with no DynamoDB table and no workspace separation, while the pipeline runs terraform apply -auto-approve on both dev and master. Both branches therefore mutate one set of real infrastructure, and two concurrent builds can corrupt the state. The feature→dev→main strategy is not actually implemented anywhere.

FixPer-environment backend config passed via -backend-config, plus locking — S3 native lockfiles on Terraform 1.10+, or a DynamoDB table on older versions.

HighThe TGW default route is imperative and invisible to Terraformmain.tf:78–90 · routes.sh

null_resource.sp shells out to a script that creates the route with the AWS CLI and swallows all errors with || true. The route is not in state, so it is not recreated if the TGW is replaced, not removed by terraform destroy, and not visible in a plan. The trigger is a hash of the script file, so it never re-runs when the infrastructure it depends on changes.

FixDeleted along with the Transit Gateway. If the optional TGW module is kept, model it as aws_ec2_transit_gateway_route.

HighNew image builds never reach running podsapp/deploy.sh:2 · app/deployment.yaml:20–24

docker tag node $REPO_URL supplies no tag, so the image is pushed as :latest. The Deployment references the same untagged repository URL with imagePullPolicy: IfNotPresent. The pod spec is therefore byte-identical between builds — no rollout is triggered, and any node that has already cached the layer keeps serving the old code indefinitely.

FixTag with the immutable commit SHA and reference by digest. This also makes ECR tag immutability enforceable.

HighIn-place sed makes the pipeline non-idempotentJenkinsfile:94–106 · app/deploy.sh:6

sed -i replaces the literal REPO_URL placeholder inside the tracked deployment.yaml. On the second run in a persistent Jenkins workspace the placeholder is already gone, so the substitution silently no-ops and whatever value was baked in previously is deployed instead.

FixRender manifests rather than mutating them — Helm values or a Kustomize image override.

HighEvery pipeline run replaces the bastion instanceami/ami.json:9 · data.tf:6–19 · Jenkinsfile:40–48

Packer runs unconditionally on every build and names the AMI bastion-ami-{{isotime}}, so each build produces a new AMI. data.aws_ami.ubuntu then selects with most_recent = true, which changes ami on aws_instance and forces replacement. The result is a destroyed and recreated bastion on every run, plus unbounded AMI and snapshot sprawl that nothing ever cleans up.

FixBuild the AMI on its own cadence, publish the ID to SSM Parameter Store, and have Terraform read the parameter. Add ignore_changes = [ami] if replacement should be deliberate.

HighNode group specifies three instance types with ON_DEMAND capacitymodules/eks/variables.tf:56–60

instance_types = ["t3.medium","t3.small","t3.large"] with capacity_type = "ON_DEMAND". Managed node groups accept a list only for SPOT; on-demand groups take a single type unless a launch template is supplied. Expect this to fail at apply, or at best for the extra entries to be meaningless. Mixing t3.small into a cluster is separately a bad idea — its pod-per-ENI limit is very low.

FixOne instance type per on-demand group, or a launch template. Confirm with a plan and apply against the sandbox.

HighElasticsearch claims 30Gi with no CSI driver and no storage classlogging/elastic.yaml:55–63

The StatefulSet has a volumeClaimTemplate requesting 30Gi and no storageClassName. Since Kubernetes 1.23 the in-tree EBS provisioner is gone from EKS, and the aws-ebs-csi-driver addon is not installed anywhere in this repo — so the PVC stays Pending and the pod never starts. The init container also uses image: "ubuntu" with no tag.

FixReplace the stack with Fluent Bit to CloudWatch. If EFK is kept for teaching, install the EBS CSI addon and pin a storage class.

HighAdding a second cluster operator requires ClickOpsmodules/eks/main.tf · repo-wide

No access_config, no aws_eks_access_entry, and no OIDC provider anywhere in the repo. The cluster falls back to the aws-auth ConfigMap, where the only administrator is whichever principal ran the first apply. There is also no mechanism for pod-level IAM, which the load balancer controller and any AWS-integrated workload will need.

Fixauthentication_mode = "API" plus access entries mapping SSO permission-set roles, and the EKS Pod Identity agent addon.

HighThe AWS provider is unpinned and the lock file is not committedprovider.tf:11–17

The version constraint is commented out and no .terraform.lock.hcl is tracked, so every init resolves to whatever is newest. Three constructs in this repo are removed in provider v6: aws_iam_role.managed_policy_arns and the inline_policy block (modules/iam/role/main.tf), and aws_eip.vpc = true (modules/vpc/main.tf:132). The repo is one init away from failing for reasons unrelated to any change made to it.

FixPin the provider, commit the lock file, then migrate to aws_iam_role_policy_attachment and domain = "vpc".

HighModules look up IAM roles they should have been handedmodules/eks/data.tf

data.aws_iam_role resolves cluster and node roles by name — roles that the same Terraform run creates. Data sources carry no implicit dependency on resources, which is precisely why module.eks2 needs a hand-written five-entry depends_on. It is a fragile pattern that hides the graph and fails confusingly on a clean apply.

FixPass module.eksrole.role_arn and module.noderole.role_arn in directly; most of the depends_on list then becomes unnecessary.

HighThe deployment stages have no branch gateJenkinsfile:76–108

Infrastructure is gated to dev and master, but "Deploy logging" and "Deploy application in K8S" are not — so a feature branch build applies manifests to the shared cluster. The application stage also depends on the kubeconfig written by the logging stage, an ordering coupling that breaks the moment either is reordered or skipped.

FixApply the same when gate, and set up kubeconfig in whichever stage needs it.

HighNothing is parameterisedlocals.tf · main.tf · provider.tf · ami/ami.json · Jenkinsfile

No root variables.tf, no tfvars, no environment separation. Cluster name, CIDRs, repository name and IAM user names are literals. us-west-2 is hardcoded in four places while the sandbox target is us-east-1, and the source AMI is a raw AMI ID which is region-scoped by definition. The original README's guidance is literally to find and replace values across all files — which is the opposite of reusable teaching material.

FixRoot variables with an environments/ directory of tfvars; resolve the base AMI from an SSM public parameter rather than an ID.

MediumThe workload manifest has no production propertiesapp/deployment.yaml · app/Dockerfile

One replica, no liveness or readiness probe, no resource requests or limits, no securityContext, no PodDisruptionBudget, no topology spread. The image is node:8.9.4 — end of life since December 2019 — installing Express with a bare npm install, with no package.json, no lock file, no .dockerignore, and running as root.

FixMulti-stage build on a current Node LTS or distroless base, non-root user, committed lock file; two replicas with probes, limits and a PDB.

MediumECR has no scanning, no lifecycle policy and mutable tagsmodules/ecr/main.tf

scan_on_push = false explicitly disables scanning; there is no lifecycle policy, so images accumulate and bill forever; and tags are mutable, so latest can be moved underneath a running deployment.

FixEnable enhanced scanning, set image_tag_mutability = "IMMUTABLE", and add a lifecycle policy retaining the last 10–20 images.

MediumDead and vestigial codemain.tf:107–160 · modules/vpc/main.tf:47–70 · modules/vpc/data.tf

module.int-bastion is created but referenced by nothing and undocumented, and shares the Name = "bastion" tag with the public one. modules/vpc creates a "default" security group allowing SSH from 0.0.0.0/0 whose sg_id output is never consumed, and a default NACL that allows everything in both directions, so it enforces nothing. data.aws_vpc.main reads back a VPC the same module just created, when aws_vpc.main.cidr_block is already in scope. A 60-line commented-out null_resource.copy-files block remains in main.tf, along with a committed modules/.DS_Store.

FixDelete. Dead code in teaching material is actively harmful — a junior engineer cannot tell it is dead.

MediumNetwork module is capped at two AZs with undocumented CIDR mathsmodules/vpc/variables.tf:1–3 · modules/vpc/main.tf:11–40

local.count slices the AZ list to the first two, and subnets are derived by cidrsubnet(var.cidr, 5, count.index + 1) for public and + 12 for private. The offsets are magic numbers with no comment explaining the intended layout. Two AZs is also below the three that EKS control plane placement and quorum-sensitive workloads want, and there is a single NAT gateway, making one AZ a single point of failure and adding cross-AZ data charges.

FixThree AZs by default, an explicit documented subnet plan, and a flag choosing one NAT (dev) or one per AZ (prod).

MediumLong-lived IAM users where SSO is already in uselocals.tf:36–45 · modules/iam/user

The stack creates a named IAM user with force_destroy = true and grants it SSM session permissions through a group policy. The project already authenticates with Identity Center — the SSO profile is in the project brief — so this is a parallel, weaker identity system creating principals that can hold static access keys.

FixGrant the SSO permission-set role instead and delete the user and group modules.

MediumPacker template is in a deprecated format with EOL dependenciesami/ami.json · ami/setup.yaml

Legacy JSON rather than HCL2. It installs python-dev, a Python 2 package absent from Ubuntu 22.04 onward, so the build breaks the moment the base image moves. kubectl is pinned to 1.23.2 and downloaded from the retired storage.googleapis.com/kubernetes-release host rather than dl.k8s.io. AWS credentials are threaded through template variables instead of the default credential chain.

FixConvert to HCL2, resolve the base AMI from an SSM parameter, drop the credential variables, and track kubectl to the cluster version.

MediumShell scripts have no error handlingbootstrap.sh · routes.sh · app/deploy.sh

None has a shebang or set -euo pipefail, so every one continues past a failed command and exits zero. bootstrap.sh passes both -P "" and -N '' to ssh-keygen along with a stray heredoc, and both routes.sh and the key-pair import end in || true, which masks genuine failures alongside the intended idempotency.

FixAdd shebangs and strict mode; replace || true with a specific check for the already-exists case. Add shellcheck to CI.

MediumNo infrastructure linting or policy scanningJenkinsfile · repo-wide

The pipeline never runs terraform validate, tflint, checkov, tfsec or any Terraform test. Sonar is pointed at sonar.sources=app — a ten-line JavaScript file — so the scanning effort is aimed at the least risky part of the repo while the Terraform, which is where the actual exposure lives, is unexamined.

FixAdd validate, tflint and checkov as blocking PR checks, and post the plan as a pull request comment.

Migration path

Each phase is one feature branch, small enough to review and demonstrate on its own — which is also what makes it usable as teaching material.

Phase 0feature/foundations
Make the repo safe to work inExtend .gitignore, pin the provider, commit the lock file, add root variables and per-environment backends with locking. Create the main branch. No infrastructure changes — this phase exists so every later phase has a reviewable plan.
Phase 1feature/network
Single VPC, three AZs, VPC endpointsBuild the new network beside the old one rather than mutating it, so the before and after can be compared and screenshotted. The Transit Gateway modules move to optional/ with their own README.
Phase 2feature/eks
Modern clusterCurrent Kubernetes version, AL2023 or Bottlerocket nodes, managed addons, authentication_mode = "API" with access entries, Pod Identity, and endpoint access configured deliberately. Role ARNs passed in rather than looked up.
Phase 3feature/ingress
Load balancer controllerInstall the controller, convert the Service to an Ingress, attach an ACM certificate. This is the phase that retires the bastion from the demo path and turns verification into a browser screenshot.
Phase 4feature/app
Application and packagingRebuild the Dockerfile, add package.json and a lock file, probes, limits and a non-root context. Replace sed with a Helm chart, tag images by commit SHA, deploy by digest.
Phase 5feature/pipeline
A pipeline whose gates can failOIDC role assumption in place of static credentials, plan-on-PR with the plan posted as a comment, apply gated by environment approval, and tflint plus checkov plus a corrected Trivy invocation as blocking checks.
Phase 6feature/observability
Logging and metricsFluent Bit to CloudWatch as the default; Container Insights or Managed Prometheus and Grafana for metrics. The EFK stack stays as an optional module for teaching what the managed service replaces.
Phase 7feature/docs
Documentation and teardownRewrite the README against the real design, embed the deployment screenshots, and write the walkthrough. Verify terraform destroy leaves nothing behind — with routes.sh gone it finally can.

Four decisions before Phase 0

Each of these changes the shape of the work, and each has a defensible answer in both directions — they turn on what the repo is primarily for.

Hand-rolled modules, or the community VPC and EKS modules? The upstream terraform-aws-modules are battle-tested and would delete most of this repo's surface area. But a module that does everything for you teaches nothing about what it is doing. Recommended: hybrid — upstream for VPC and EKS so the demo is production-credible, with the hand-rolled versions kept as an annotated teaching chapter showing what the module generates.
Jenkins, or GitHub Actions? Jenkins can be modernized in place, but the OIDC federation that removes static AWS credentials is far simpler on Actions, and the repo already lives on GitHub. Recommended: GitHub Actions with OIDC, keeping the Jenkinsfile briefly as a comparison artifact if the audience is likely to meet Jenkins in the field.
How private should the endpoint be? Option A is easiest to demonstrate; option C is closest to what an enterprise actually runs and forces you to teach VPC endpoints. Recommended: option B — private access on, public access restricted to a small allowlist, SSM port-forward for anything outside it.
Managed node groups, or Karpenter? Managed node groups are simpler to explain and one variable away from working. Karpenter is what most teams building new clusters now reach for, and its bin-packing behaviour is genuinely interesting to watch in a demo. Recommended: managed node groups first, Karpenter as a later phase once the stack is green end to end.
